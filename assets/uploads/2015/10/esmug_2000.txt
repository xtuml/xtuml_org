When you have been pushing bits from one pile to another for
as long as I have, the piles all start to look the same
after awhile.  [I've been looking for a button to wear at
work that says, "Show me the Package!", but I can't find
one.  But I digress...]

FWIW, I think design patterns are the next step along this
path.  We started out cobbling bits together, moved on to
instructions, language statements, objects, and now design
patterns.  Similarly, the basic flavors of S-M architectures
are flavors of computing environment context.  It wouldn't
surprise me if a decade of so in the future one had
application patterns.

An interesting variation on this theme, BTW, is the current
proposal to OMG for action languages.  As I understand it
the proposal involves the notion of distinct executable
frameworks that combine a particular executable subset of
UML with an action language.  I can imagine such frameworks
being customized based upon class of application.

In reality, though, I suspect the future lies in components
(nee domains).  People will still cobble together
applications but the level of abstraction of the components
will be more general.   Bertran Meyer once said that he saw
Eiffel as just a tool that allowed him to get into the
really lucrative market of creating and selling components.
I'm not so sure he has succeeded in that, but it seems to me
that an OTS domain OOA should be marketable because (a) it
is truly plug & play into any S-M development environment
and (b) since it is simple and unambiguous it is the best
form of source distribution.  Not to mention that it is a
whole lot easier to port across platforms.

it.  If a problem doesn't fit a know context, then invent a new one.

Complex systems include many different types of problems so they could
have multiple types.

Subject: (SMU) Using Inconsistent Populations
David.Whipp@infineon.com writes to shlaer-mellor-users:
--------------------------------------------------------------------

An OOA model defines what a consisent population is. It defines the 
attribute-domain for every value; and the multiplicity/conditionality of 
all relationships. It is often assumed that an architecture will be 
designed to work with consistent data.

But consider a User Interface. Users like to enter incomplete and/or 
insonstent data. For example, if I'm editing an SM model then I might 
create 2 objects with the same name; or omit an attribute-domain. I might 
want to save it in this inconsitent state. I might even want to run a 
model-checker tool to find my mistakes.

There are two ways to model this situation. One is to explicitly model all 
the things the user might want to do wrong. So you might make all the 
relationships Mc:Mc; and only use arbitrary identifiers. The other way is 
to model the correct information; and build a special architecture that 
permits the manipulation of inconsitent models.

I think the the latter method is self-evidently superior, but I often find 
myself falling into the trap of modeling too much flexibility into a 
domain. How do other people deal with this aspect of user interfaces? Is 
the manipulation of inconsistent data useful in other problem areas?


Dave.

I'll try to explain why I don't like that approach. To
to so, I'll take it to an absurd conclusion.


Imagine youare writing a word processor. You decide that one
of your domains is a "Language" domain, that 'understands' the
document and whose population is only consistent when every
word is spelt correctly.

Using the approach of "the tool should not allow inconstent
data" we might construct the user interface is such a way
that when the user enters an incorrectly spelt word, a
dialog box immediately appears to ask them to correct/add/
ignore the word. This is the absurd end-point: an word
processor that is probably unusable.

If you compare this approach to, say, MS Word's, then I
think that the MS approach is far more user friendly. You
simply underline the word in red, and allow the user to
continue typing. A user can save/load inconsitent
documents; they can run grammar checkers; they can
print it, etc.

I know that this analogy breaks down at some level; but
the crucial lesson is that users don't want to correct
their errors immediately. We need to manipulate incorrect
data.

So I return to the original point. Do we allow this
desirable user-interface behaviour to impact the models
of the rest of the application; or do we construct the
user interface around a special architecture that can
handle the incorrect data (and, indeed, know that it
is incorrect because it doesn't match the application
model's definition of correct)

I think that Chris Lynch's suggestion that coloring
the application model to suggest what errors can and
cannot be handled would be useful refinement; but only
after you take the fundamental decision that the
architecture will handle the inconstent data.

Responding to Whipp...

> I think the the latter method is self-evidently superior, but I often
> find myself falling into the trap of modeling too much flexibility
> into a domain. How do other people deal with this aspect of user
> interfaces? Is the manipulation of inconsistent data useful in other
> problem areas?

We usually handle this essentially the way Riemenschneider
suggests.  Most basic input checks are done in a <realized>
Validation domain that is pretty dumb and is created from
spreadsheet data describing the hardware specifications of
the particular system.  This is done for the core instrument
driver for individual API calls; it doesn't understand
complete tests, just valid individual requests.

We also have editors for developing test programs that
explicitly handle checking in their domains.  These will do
simple checks of individual values on entry and more
complete checks of attribute combinations at key points like
a Save.  These domains understand a complete test and
provides that level of consistency.

In certain situations where we translate from other test
program development systems (e.g., an ATLAS environment) we
have an intermediary domain similar to a GUI that will do
specialized checking.  For example, the %&*@#%! ATLAS
digital specification requires that one save a host of
information temporarily because it cannot be validated until
one is actually ready to run a particular test burst.  So
everything is stored in the intermediary domain and it isn't
actually sent to the test instrument until ATLAS requests
execution.

We do an explicit validation at that point before setting up
and running the test on the hardware. If an problem is
found, we return an error to the client at that point
without sending anything to the application.  This is all
done explicitly in the OOA because it is a pretty basic
characteristic of the problem space environment.

The bottom line is that I don't think one 'manipulates'
inconsistent data.  One accepts the data provided by the
user and checks for errors at the earliest opportunity.
Basically our approach is not to commit the data from the
user interface to the rest of the application until it has
been verified for consistency.  The tricky part is finding a
time to do that.  In the ATLAS environment there is no
convenient time until the moment of execution.

Assigners in Shlaer-Mellor permit two state machines to exist within a
class, although one of the state machines is a singleton - only one
instance of the assigner state machine would exist.  This does not
exist in UML, so you need to create a separate Assigner class to hold
the state machine.

If you only need one assigner, you instantiate one instance of the
class.  Since there are cases where you'd want multiple assigners to
manage non-overlapping sets of resources, you can instantiate as many
as you need.  The commonly cited example is the Customer-Clerk
assigner, where Clerks only serve certain departments, and you'd have
one assigner for each department.

The general UML assigner IM pattern looks like this: <fixed font>

Consumer__0..*____________________0..*__Resource
   |                  |                     |
   |0..*              |               0..*  |
   |             Matched Resource           |
   |                      |  0..*           |
   |                    1 |                 |
   |_______________1__Resource Assigner__1__|


The UML state model pattern looks pretty much the same as the
OOA/RD pattern.

Hope this helps.

Greg

The identifier that you have to worry about constructing is
the supertype's.  The way to think of sub-/super identifiers
is from the bottom up.  If the lowest level subtypes have
unique identifier domains among themselves, then their
immediate supertype simply has the same identifier.  If the
identifier domains overlap, though, there is a problem in
that the supertype model instance identifiers associated
with two different subtypes could be the same.  So the
supertype has to have an additional identifier that will
make it unique.  Basically you use this same logic all the
way up (down?) the tree.

We are considering two objects, O1 and O2. There is a 1:1 relationship,

A transitive dependency arises when A->B, and B->C, but B!>A. ("A->B" 
indicates
that B is functionally dependent on A, and "B!>A" indicates that A is not
functionally dependent on B.) (If we didn't add the final condition, B!>A, 
we
would be prohibiting all secondary identifiers.) This is nothing more than 
a
formal statement of the condition where an attribute of an object is 
dependent
on a foreign key, which I originally offered as the definition of NF3. 
Formally,
a relation (object) is in NF3 if there are no transitive dependencies 
WITHIN THE
OBJECT, and a database (OIM) is in NF3 if it contains no relations 
(objects)
which are not in NF3. Read any book you like, they'll all agree with this
paragraph. The immediate conclusion is that there can never be a transitive
dependency between relations (objects), supporting my claim.

We can, however, analyze further to remove any doubt. Continuing my example
above, let A1, B1, and C1 be non-key attributes of O1, and A2, B2, and C2 
be
non-key attributes of O2. Obviously we can say that K1->A1, K1->B1, K1->C1,
K2->A2, K2->B2, and K2->C2. No transitive dependency yet. We can go 
further to
say that K1->K2 and K2->K1 because of the 1:1 relationship R1. Therefore 
we can
say that K1->K2 and K2->A2. But this is not a transitive dependency because
K2->K1, and thus K1 and K2 are interchangeable, establishing my original 
claim.

Conclusion: when a 1:1 relationship exists between two objects, you could
combine the two into a single object using either primary id as the 
combined
primary id. Or you can let each object have its own distinct primary id. 
Or you
can formalize the relationship using the primary id from one object, and 
then
name that attribute as the primary id of the second object as well. They 
all
work, they all fit the rules. Do what makes sense in your situation.

This seems to violate 2 rules: "one fact in one place" and
"attributes are atomic".

The first is violated because the tag always matches the class
name. The second is violated only if the composition is
visible in the OOA. However, to have the behaviour you ask
for, it must be visible.

Analysis is meant to be explicit. Multiple identifiers
allow you to express precisely what you are wanting to
say:

 "All vehicles have a unique identity (the supertype
 identifier). Different types of vehicles have thier
 own ways of describing thier identity (identifier
 of subtypes). The subtype identifier is equivalent
 with the supertype's (this equivalence is obviously
 not transitive: card(super) > card(sub))"

The equivalence of the identifiers is formalised by
including both the supertype and subtype identifiers
in the subtype. One is primary, the other secondary.

Even RTTI is possible. You can ask if an instance
with a specific identifer exists. Alternatively, a
"find one" accessor can have a control output that
tells you when none is found.

If you want to stick with single identifers in an
implementation then you add a rule into the translator:

 "If all the subtypes of a supertype have secondary
 identifiers, and then created a tagged datatype that
 unifies the subtype identifiers. If the supertype
 identifer is arbitrary, then dispose of it in favour
 of the new tagged identifier. Otherwise ..."

Good question, and one that, I presume, many of us have pondered.

The reason this quandary exists is that there seems to be two different
ways to formalize R1.  If you create an instance of Object B and set
attribute p1, then you would think that R1 is correctly formalized.
However, most of the action languages require you to explicitly link
R1, which will also set attribute p1.

If attribute p1 is not an identifier of Object B, then I would suggest
that you not set p1 upon creation of B, but then immediately link R1
causing p1 to be set correctly.

If p1 is an identifier of Object B, then p1 must be set upon creation
of B.  In this case, you still want to link R1 after the creation of B,
but the link should not overwrite p1, since identifiers cannot be
changed after creation.  Depending on your architecture, there could be
some error checking inserted here to ensure that the instances linked
have the same value for p1.

At the last user's group conference, it was suggested that we should be
able to completely eliminate referential attributes when using a UML
notation.  This would remove this quandary, and relationships would
just be formalized using some type of link.  The way the link is
actually remembered would be architecture dependent (which it already
is, really) and there would be no evidence of that on the information
model (class diagram).

The big downside to this is that you would no longer be able to
constrain relationships with merged referential attributes (i.e. one
referential attribute formalizing two or more relationships).  These
constraints would have to be annotated on the class diagram in some way
and enforced by the actions.

Any opinions out there?  (It's been pretty quiet lately.)

First of all (as Terry Gett writes) p1 by itself is a not correct

referential attributes) that's led to the notion of dropping the
referential attributes from the Information Model (UML class diagram).

Ok, despite the wonderful theoretical discussion that's going on--which,
btw, I live for and will soon join--there's a practical question: what
should this person do in this situation now with OOA in its current state
and given existing tools. Here's my take:

1) Fix the identifier in B. You can't give the same identifier value to
more than one object, but given the way you have modeled it, that is what
will happen when you create more than one B associated with any given A.

2) Stop thinking of the relationship and the formalizing attribute as
different things. They are just two views of the same concept, namely that
there is some kind of affinity between A and B. Specifically, for any A
there can be 0 to many related B instances, and every B has a related A
instance. Most modeling tools will treat the relationship as something
distinct from the attribute, but you should not think of them in this way.
(To theory buffs: I know, it's deeper than this. I'm trying to be practical
in this post. We can have a flame war on theory in another thread, eh?)

3) Do not leave the creation state of B (assuming self-creation) or the
state in which B is created (assuming other-creation) without "linking" A
and B, or without providing a value for p1 in B. The specifics will depend
on the action language that you use. In my case, I say (from within B's
creation state) "relate self to A across R1". This automatically links the
instances AND fills in the value of p1 in B. Your language may vary, but
the concept will not. Even if it is legal to create a link without placing
a value in the formalizing attribute, or vice versa, don't do it.

Hope this helps.

The original OOA information model is based on the relational database
schema.  Every object has enough information in its attributes for you to
go and look up a related object in a table.  Very simple really and
everyone understands it.  Its what makes the method so appealing to those
of us from an Information Systems background.

Now, a lot of people using the method are not from an IS background, but
are coming from a real-time perspective.  They look at this slow table look
up mechanism and say, 'Couldn't we just use pointers?'  Well, sure you can,
but its a lot of hassle for the architects to auto-magically convert the
method's relational model into an architect's pointer-based model.  The
solution adopted by the CASE tool vendors is to introduce the link/unlink
and navigate operations and make the analyst do the work.  The KC ASL
allows you to set relational attributes and use 'find' operations to
retrieve instances, but it also supports a parallel link operation, which
establishes a pointer between two instances, and a navigate, '->',
operation that lets you retrieve the instance(s) that are being pointed at.
 This is inherantly faster than a table lookup and suits many in-memory
applications.  Another action language I know of has completely disposed of
referential attribute assignments in favour of linking and unlinking.  You
can still read a referential attribute in this AL but, under the hood, this
is accomplished by a navigation and a read.

The use of link/unlink and navigate operations seems, IMHO, to be a case of
the architecture polluting the analysis.  Okay, its done for pragmatic
reasons, but it is still pollution of the original S-M concept and, because
these ASLs are now mixing the relational and pointer-based abstract
architectures, it is no surprise that conflicts and inconsistencies can
arise.

I shall probably be burnt as a herectic for saying this, but I also think
that wormholes and synchronous services represent architecture creeping
into the analysis.  Anyone care to light the first match?

Object Software Engineers Ltd.

ian@kc.com (Ian Wilkie) writes to shlaer-mellor-users:
--------------------------------------------------------------------

As one of the creators of one of the Action Languages being discussed,
I can state that the reasons for choosing to have link/unlink primitives
were (as we presented at the SMUG meeting in 1994):

- Volatility of referential attribute expressions

  As the OIM evolves, any change to the identification of Objects
  or to the pattern of formalisation involves changes to the users
  Action Language code.  Without complex tooling the user must maintain
  a lot of information by hand.

- Bulk of referential attribute expressions

  It is not uncommon for Objects in a complex model to have four or
  five identifying attributes.  Users must write 5 attribute assignments
  in order to express the simple idea that instance "a" gets related to
  instance "b".  Not only is this hard to write, but also hard to read
  and obscures the intent of what is going on.  If you extend this to
  a whole series of navigations across a model, then you can end up
  with a large number referential attribute accessors where an Action
  Language can (as Peter has observed) simply say:

     source_location = this -> R6.ONLINE_DISK -> R7.SLOT -> R11

- Questionable semantics

  As Bary and Marc have observed, it is possible to create referential
  attribute manipulations that have questionable meaning.  For example,
  what if only one of two referential attributes for a relationship are
  set.  Has the relationship been established or not ?

Now, I am not claiming that a language such as ASL eliminates all of
these issues.  For example, the ASL is still volatile against OIM changes
(but not identification/formalisation changes).

Of course, it would be disingenuous of me to claim that I was not aware
that link/unlink primitives would make it easier to implement relationships
as efficient pointer manipulations.  However, this was not the primary
concern.  ASL was developed after our consultants had experienced about
2 man years of work on a system with a customer written action language
that used referential attributes.  We saw what the problems were and we
addressed them.  We created an Action Language that we thought helped
analysts better understand the problem and express the desired behaviour.

ASL addresses the potential for inconsistency between link/unlink and
referential attributes with the rules:

- When an object instance is created it must have a fully formed
  identifier (i.e. all the identifying attributes must have values,
  including those which are also referential)

- Aside from referential attributes that are part of an identifier,
  user ASL must not set the value of referential attributes

- When a link/unlink is executed, the referential attributes which
  are not part of an identifier have their values automatically set
  by the formalism

- In the case of referentials that are also part of the identifier,
  when a link is executed, if the value of any identifying attribute
  does not agree with that of the object to which it is referring,
  then this is considered to be a run time constraint violation.

This reduces the potential for inconsistency to similar levels as
for other aspect of the formalism.  For example, it is quite possible
(whether using referentials or link/unlink) to create a process model
which does not respect mandatory relationships.  In this respect,
I think of the OIM as a statement of requirement/intent with which the
process model must agree at run time.

Given these rules, an architecture is free to implement relationships
in any way it chooses:

- Pointers vs Foreign Keys
- Automatic setting of referentials vs replacement of referential reads
  with navigate and read

and so on.

Regarding the steamlining of the method to remove identifying attributes
and referentials, I would observe:

1. In many cases, explicit modelling of identity and use of referential
formalisation is a useful activity.  It is another tool in the analysts
toolbox for exploring a subject matter.  I often find when I realise
that when a relationship formalisation requires an attribute with the
same name as an existing attribute (and hence has the potential to be
merged), that a whole new aspect of the subjet matter has been brought
to my attention.  I also find appropriate identifier construction to
be a more readable way of expressing a composition/ownership relationship
than the UML composition diamond, but that is just personal taste.

2. On the other hand, there are many (particularly highly abstract) domains
where there is little or no intrinsic identity in the subject matter other
than "arbitrary".  Sometimes there is also little in the way of merging
of formalisations either.  In such cases it might be nice to be able to
forget about explicit modelling of identity.

3. UML does not have the formal notion of subject matter related identity
nor referential attributes in the SM sense.  However, UML does not exclude
the definition, as part of a profile, of such concepts.

Steve Mellor, myself and others have been working on the idea of such
an "Executable UML" profile.  I think that in such a profile it makes sense
to say that explicit modelling of identity and referential attributes
is optional.

The major component missing for such a profile is, of course, any kind
of fully and rigorously defined action semantics in UML.  The OMG has 
issued
an RFP for an extension to UML to address this for which the initial 
submission
date has just passed (August 15).  There was only one submission, by a
consortium that includes several Shlaer-Mellor players as well as Rational
Software and you can find it at http://www.umlactionsemantics.org.

To bring the discussion full circle, this submission has the idea of
primitive link/unlink/navigate actions and does not use referential
formalisation.  Having said that however, there is nothing to stop
you creating a surface language that uses such referential manipulation
but which is defined to map on to the underlying primitive actions.

Regards,

Ian Wilkie.

"Stephen Mellor" <steve@projtech.com> writes to shlaer-mellor-users:
--------------------------------------------------------------------

Two points to add to the fray...

First the "architecture pollution" issue.  Any executable formalism
runs the risk of being seen as "the way it's implemented."  But to
be executable, you gotta write it down somehow.  The way to think of
it is in a manner similar to that taken by a Prof of mine long ago.
He said:  "Once you express any abstract syntax, it becomes concrete."
In other words, we can express the "abstract syntax" of Java, say, by
talking about the components that make up the language, but the moment
we write it down somehow, and use the word "class" or "gobbledegook",
we have made the syntax concrete.  But now some lunatic is going to
begin ranting about the underlying (abstract) language in terms of
"Well I don't like the word 'class'."  Sigh.

Second, we can turn this question around and ask it the other way:
If we didn't have referentials and identifiers, what (technically)
would we lose.  IMO, the answer is: Two kinds of constraints.

The first kind I'll call "uniqueness constraints"  e.g. I can't have
two students with the same Student number.  Adding a student number
to the class helps us retain the student's number, but it doesn't
say that the student numbers must be unique.

The second kind is "relationship constraints."  These constraints
are those of composed or constrained relationships that adhere to
sets of associations: the famous Student-Professor-Department
example is one.  Although we happen to build one association as a
composition of the other two, that's partly an artifact of the
mechanisms we use, namely referential attributes.

Both of these types of constraints can be expressed using UML's
own Object Constraint Language (OCL).  If we used OCL to fill in
the gap caused by the removal of identifiers and referentials, we
would be able to say all that is important without "cluttering up"
the class diagram (of course, one person's cluttering up is another
person's critical information, but you get my drift.)

The OCL follows some general patterns in each case, and can easily
be recognized without writing a pile o' syntax (hence, we would see
patterns: The Uniqueness Constraint, The Composition Constraint, etc)
Architectures would have to adhere to these constraints, and all
model compilers could then be able to assert which constraints
they satisfy at run-time/compile time/at all.  Some could even
check arbitrary OCL constraints.

But I get ahead of myself.  My point is simply that "identifiers"
and "referential attributes" exist in two dimensions: as artifacts
of some concrete representation of an abstract syntax, and as
solutions to certain identified (sorry :) problems: the specification
of the existence of these two types of constraints.

Yes, we can do without identifiers and referentials.  But we have
to decide if we can live without the ability to specify constraints.
And, if not, what we replace that specification mechanism with.

-- steve

I won't argue with you about graphics vs text-languages.  One thing I've 
grown
to appreciate in my experience modeling with implementation-language 
actions,
ADFDs,
and textual-based action languages is that specifying action semantics in 
an
analysis-based language is very important for the following reasons:

* ease of modeling - action languages tend to higher level so there is 
less for
the
analyst to write and more for the translator to automatically generate.
For example, linking associations, performing a find, and navigating
associations are all
primatives.

* flexibility of implementation - If you are coding actions in an
implementation language
the analyst must be intimately familiar with how the analysis concepts 
such as
associations and event generations
are implemented.  The translator can generate many helper functions for 
you but
you
still have to remember which one to call.  Also, if you want to change how 
an
analysis
concept is mapped, it is likely you will have to recode actions.

* potential for optimization and instrumentation - Once the translator 
knows
about action semantics
there are a lot more opportunities for optimizing and instrumenting the
generated code.  For example,
an obvious optimization is to only implement an association in the 
directions
it is traversed.  Using action
semantics you know exactly where associations are traversed and you can 
figure
out the directions.
If you are using C++ for your actions, you would have to parse C++ (a scary
proposition) and reverse engineer it
to figure out where the navigations are.  Alternatively you could put the
burden on the analyst to
specify which directions to implement the association. I don't consider 
either
of these options optimal.
Suppose you wanted to instrument the code generated from your model and 
wanted
to trace when
an association was navigated.  Action semantics know exactly where the
association is navigated
and can insert the appropriate instrumented code.

of a single domain they are random value generators.
>From the perspective of a single domain, an
asynchronous wormhole is little more than a comment
(there is an implicit assertion that some future
event will happen, sometime before the end of the

What's all this got to do with primitives? Well,
under these definitions, the only primatives needed
are accessors: creation, delete, and attribute
manipulation (if you like links, then add these,
too). All other operations can be defined in
appropriate service domains. For example, a string
is a type that references an object in another
domain. This object has a relationship with a
character object, with some means of ordering
(e.g. an assoc object). It'll probably get rather
tedious to define all these things!

Everything needs to be grounded somewhere. There
are some essential concepts that cannot be omited
in a turing-complete formalism. Basically, you need
some concept of value, plus conditionality and
multiplicity. To be useful, we need a bit more than
the minimum. OOA is not the best approach for all
domains. Sometimes pure mathematics is superior.
Whilst it is possible to model integer arithmetic
in OOA, I would much rather use second order
predicate logic.

So, when I get away from pure philosophy, and try
to be practical, what do I want?. First, the action
language must allow me to manipulate values, and
groups of values. (This is required by the RFP).
Life would be easier if these groups could be
manipulated with set, bag, and sequence semantics.

The only primitive transforms would be those
required to manipulate these containers. If a
string is a sequence of characters, then it can
be manipulated as a sequence. If we want to obey
the rules of normalisation, then the non-atomic
nature of the string must be hidden in a (standard)
service domain.

Some primitive tests are also needed. To facilitate
this, types should be associated with an ordering
property: nominal, ordinal, (possibly interval, ratio),
plus the concept from the SM Types paper: graph-based
ordering. It is possible for one type to be associated
with multiple orderings and equivalence classes, and
so "test" processes should choose the appropriate
one(s). (e.g. case sensitivity). (Quick note here:
"test" processes do not output built-in boolean types:
they output [0,*] control flow activations)

This implies that the definition of a domain's types
should become an important part of the analyst's role.
The definition of an attribute domain (i.e. its type)
must define legal values, ordering properties, and
available transforms for the type. Obviously tools
and/or syntax may provide shortcuts for commonly
used types. But from the sematics viewpoint, there
is no need for special cases as primitives.
